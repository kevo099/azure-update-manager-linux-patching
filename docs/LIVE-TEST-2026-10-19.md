# Live test — 2026-10-19

The [guide](GUIDE.md) was run in a pay-as-you-go subscription, in one resource group in Central US. Not
exercised: Azure Arc, a disk rollback, a freeze set through `frozenRings`, the remediation branch of
`scripts/onboard-policy.sh`, and the final runbooks' change-freeze and cancelled-run paths (an earlier
revision ran them; see below). Tenant, subscription, principal and run identifiers are
omitted; resource names below are the repository defaults.

## Environment

- Azure CLI 2.91.0 with the `maintenance` 1.2.1, `resource-graph` 2.1.1, `automation` 1.0.0b2 and
  `scheduled-query` 1.0.0b2 extensions; Bicep through `az bicep`.
- Four `Standard_D2als_v7` VMs from the latest marketplace images: Ubuntu 24.04 LTS and Debian 12 in
  ring 0, RHEL 9 (pay-as-you-go, LVM) and Azure Linux 3 in ring 1.
- A private subnet with default outbound access off, a NAT gateway for egress and an NSG with no inbound
  allow rules. All four VM agents were `Ready`. The Microsoft, Debian and Red Hat repository endpoints
  answered HTTPS probes from every VM; the Ubuntu mirror did not answer an HTTPS probe, but Ubuntu's
  assessments and scheduled run, which use its configured apt sources, succeeded.
- The VMs were created with `patchMode` and `assessmentMode` `ImageDefault`, so onboarding was left to
  the policies.
- First assessment (on demand): Ubuntu and Debian up to date, Azure Linux 21 updates, RHEL 112
  Critical/Security and 44 Other.
- To give ring 0 a real security update, Debian's `openssl` and `libssl3` were downgraded to
  `3.0.20-1~deb12u2` before the scheduled run.

## Review and fixes before publication

Two read-only reviews (four reviewers, each finding checked by an independent skeptic against the code
and Microsoft's documentation) ran while the lab was live. The first confirmed 37 of 41 findings; the
second confirmed that all of them were fixed and found 15 smaller issues, which were also fixed. The
ones that changed behaviour:

- **The change-freeze cancel would have been refused.** None of the four built-in roles first given to
  the hook identity grants `Microsoft.Maintenance/applyUpdates/write`, so the cancel PUT would have
  returned 403 and the frozen run would have patched. The script now creates a resource-group custom role
  with only the actions the runbooks use; the 09:30 cancel above ran with it. Virtual Machine Contributor
  (which includes Run Command), Disk Snapshot Contributor and Scheduled Patching Contributor were removed.
- **Webhook renewal.** Expired webhooks cannot be renewed and the first version never re-pointed the
  event subscriptions. The script now records each webhook's creation time, recreates both webhooks when
  they are missing, disabled, replaced or near expiry, and re-points every subscription that used them.
- **Event validation.** The webhook URL is the only credential, so the runbooks now check the event type
  and the exact configuration and run ID shapes, and send the identity's token only to Resource Manager.
- **Run membership.** The pre-event handler takes the machines from the run's own records (as Microsoft's
  sample does) instead of rebuilding them from tags; the post-event handler reports installations that
  carry the run's ID instead of anything in the resource group after the window started.
- **Snapshots and starts.** Snapshots are named after the run (a repeated delivery reuses them), checked for
  a final `Succeeded` state, and started machines are waited for; late events change nothing.
- **Templates.** A change freeze is a template parameter (`frozenRings`), so a redeploy that passes it keeps
  the freeze (any redeploy used to remove a hand-added tag); multi-region groups are supported
  (`machineLocations`), alerts are raised per machine, and alert role assignments no longer collide after a
  rule is recreated.

## Gotchas found during the test

- A run cannot be read back through ARM: `GET` on its correlation ID returns `400 InvalidResource` at
  every API version tried, so the handler reads run status from Resource Graph.
- `patchinstallationresources` rows of scheduled installations carry the run's correlation ID in
  `maintenanceRunId`; on-demand installations leave it empty.
- The post-event's `EndDateTime` is the actual end of a completed run but the window end of a cancelled
  one.
- The Maintenance resource provider answered the static configuration assignment's write with
  `GatewayTimeout` although it succeeded; reading the resource back avoided duplicate retries.
- The runtime environment's `provisioningState` stayed empty after creation, so waiting for `Succeeded`
  times out; check the default packages instead.
- `az monitor scheduled-query list` shows the alert rules' identity as `None`; `az rest` with API
  `2023-12-01` shows the system-assigned identity.
- The Resource Graph extension prints only counts with `-o table` unless the query selects `data`
  (`--query data -o table`), which `scripts/report.sh` does.
